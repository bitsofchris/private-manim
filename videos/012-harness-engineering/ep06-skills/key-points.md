# Ep 6: Skills: procedures the agent can load (key points)

**Status:** research done 2026-10-16, not yet scripted. Sources read: 9 external (Anthropic engineering post; Agent Skills docs overview; skills survey 2605.07358 in part; SkillsBench 2602.12670 abstract v1 and latest plus the self-generated appendix; MemSkill 2602.02474 in part; SkillForge 2604.08618 in part; Voyager abstract) and the AugiCraft repo (README, `docs/CAPABILITY_DEVELOPMENT.md`, `knowledge/core/MAP.md`, the door skill, two door episodes, one deprecated skill, `runtime/memory/store.js`, commit 532f3cd), plus 7 vault notes.
**Question:** What are Claude skills / agent skills, and how do I write ones that actually help?
**Who's asking:** a Claude Code user who has seen `~/.claude/skills`, maybe used skill-creator, and isn't sure skills are more than saved prompts.
**Answer in one sentence:** A skill is a procedure that worked, saved where the agent can find it by a one-line description, and it helps only if it's written from a real run and checked again. Skills an agent writes from scratch before doing the task made agents worse.
**Search phrase:** claude skills explained / agent skills (guess).
**Length:** Short + companion. The core (what a skill is, the bot's door skill, the "write it after, not before" finding) fits 75–90 s. Progressive disclosure detail, the survey's lifecycle, SkillForge and MemSkill go in the companion.

## Key points, in episode order

### 1. A skill is a folder with a procedure in it, and the model only sees its one-line description until it needs it.
- **Say it:** A skill is a folder with a SKILL.md file: a name, a description, then the steps. At startup the agent loads only the name and description of every skill, about a hundred tokens each. When a task matches the description, it reads the full file, and only then any extra files or scripts. So you can install dozens of skills without filling the context window.
- **Evidence:** Anthropic engineering post (Oct 16, 2025): "At startup, the agent pre-loads the name and description of every installed skill into its system prompt." Linked files are "the third level (and beyond) of detail, which Claude can choose to navigate and discover only as needed." Docs overview: Level 1 metadata "~100 tokens per Skill", Level 2 body "Under 5k tokens", Level 3 "None until accessed". Scripts run through bash, and "only their output enters context". Description max 1,024 characters. It "must say both what the Skill does and when to use it." Checked: blog + docs, full.
- **Chris's own line:** "A repeatable unit of work for Claude to do." and "New skills take very little context to load." From [[2026-01-17 - Learning Claude Skills]] *(Chris)*.
- **Visual:** a wall of sealed cartridges beside the pipes. Only the label shows. The blob reaches for one, the cartridge opens, and its procedure flows into the pipe.

### 2. Skills are the "how", which tools and memory don't give you.
- **Say it:** A tool says what the agent can do. A skill says how and when: the order, the checks, what to do when it fails. That's the gap skills fill. It's procedural memory you keep in files instead of in the weights.
- **Evidence:** Skills survey (Zhou et al., May 2026), §II-C: "A tool exposes an atomic capability: it specifies what can be done, not how it should be used." MCP solves "an interoperability problem, not the procedural problem." Definition 1: a skill "externalizes task-focused know-how: not only what can be done, but when to act, how to execute, what heuristics and failure modes matter, and how to judge completion." Anthropic's analogy: "Building a skill for an agent is like putting together an onboarding guide for a new hire." Checked: survey intro and §II in full; blog.
- **Chris's own line:** "Everything is a file - easy interface to store and pass context … One tool / small tools chained together - making lots of CLIs - specific to your use case, then it's easier for agent to do stuff … Are claude skills a way to do this?" From [[2026-01-21 - Unix philosophy - cli for agents]] *(Chris)*. Shorter alternative: "The Unix hive mind - skill files the right idea. Compaaable and reusabla that’s how it scales to hive mind" ([[2026-02-10]], verbatim with typos; fix spelling on screen, not in the quote).
- **Visual:** a pipe labeled `set_door` (the tool) next to a cartridge labeled "return to base" (the skill) that routes through `observe → navigate → set_door → navigate → deposit`.

### 3. The demo: the bot got stuck at a door, built the missing tool, and saved the procedure as a skill.
- **Say it:** On 10/12 my Minecraft agents kept getting stuck at the house. They couldn't get through the door. They have standing permission to build a missing action when blocked. So an agent wrote a small door tool with tests, found the real bug (the pathfinder treated an open door as a wall), tried it live, and then wrote the procedure down as a skill: walk to the entrance, check the door, open it, step inside, verify, deposit. The skill was promoted only after it worked on a second, separate run.
- **Evidence (AugiCraft repo, read directly):**

### 4. The thing most people don't know: a skill written before the work makes the agent worse.
- **Say it:** Here's the result that surprised me. A benchmark gave agents skills written by experts and they improved by about sixteen points. Then it had the agent write its own skills first, using Anthropic's own skill-creator, before solving anything. Those agents did worse than with no skills at all: Claude Code with Opus 4.7 dropped eight points. A skill invented from the model's priors is just a confident guess written down. My bot's door skill is the opposite: it was written after the door worked, from what actually happened.
- **Evidence:** SkillsBench (Li et al., arXiv 2602.12670). Latest version: 87 tasks, 18 model-harness configurations, curated skills raise pass rate from 33.9% to 50.5% (+16.6 pp). Self-generated condition (Appendix D.6; creator session with skill-creator and no solving, then a clean solver): below the no-skills baseline on all three configs, −8.1 pp Claude Code + Opus 4.7, −11.3 pp Codex + GPT-5.5, −11.5 pp Gemini CLI + Gemini 3.1 Pro. Curated skills added +18.2 to +24.8 pp on the same configs. v1 abstract: "Self-generated Skills provide no benefit on average, showing that models cannot reliably author the procedural knowledge they benefit from consuming." The audit's causes: packs never read ("10 of 12 audited trajectories never list, read, or mention the generated skills"), authoring eating the solver's budget, and "confidently wrong" content. The one big win was "leakage, not reuse". Checked: abstracts (v1 and latest) and Appendix D.6 text.
- **Chris's own line:** none fits. Don't force one.
- **Visual:** two cartridges. One is stamped "written before" and is empty, with a question mark. When loaded, the output blob goes lumpy. The other is stamped "written after ✓✓" and the blob comes out sharp.

### 5. So: write it from the run, keep it as a candidate, promote it when it works again, retire it when it's wrong.
- **Say it:** The pattern that works is the one my bot follows. Save the skill right after a real success, from the trace, including what went wrong. Mark it a candidate. Promote it only after it works again on a separate run. Retire it when the rules change. The research survey lands in the same place: skill libraries only get better when every change passes a check before it's trusted.
- **Evidence:**
  - AugiCraft README: "new skills start as `candidate`. `kb_promote` needs `promotion.minSuccesses` successes from distinct episodes" (set to 2). "Near-duplicates and seed shadowing are refused, which pushes the agent to compose existing skills" (`store.js` refuses at Jaccard ≥ 0.5 unless forced). The MAP today: 3 validated, 12 candidate, 1 deprecated. The deprecated one carries its reason: "Chris explicitly changed policy: automatic defense must stay local and never return to base."
  - Survey §VI-F: "The evidence for skill evolution is strongest when a method directly modifies a named artifact and exposes a check on the update." It also lists "admission quality at scale" as an open problem: low-quality skills accumulate faster than libraries can validate them.
  - Anthropic's own guidance matches: "Start with evaluation … Then build skills incrementally" and "Iterate with Claude: … ask Claude to capture its successful approaches and common mistakes into reusable context and code within a skill."
  - Checked: AugiCraft files read directly; survey §VI–VII; blog.
- **Chris's own line:** none verbatim on promotion. (His "fails-twice rule" is in the 6/12 draft outline, but only as a phrase.)
- **Visual:** the cartridge shelf has three rows: "candidate" (dim), "validated" (lit), "retired" (greyed, with a note pinned on).

### 6. Code for the parts that must be exact, words for the judgment.
- **Say it:** A skill can carry scripts. Use them for anything that must come out the same every time, and keep the judgment in plain steps. My bot splits it hard: game actions are tested code, and the skills it writes are plain Markdown plans that call that code. The skill writer rejects any code.
- **Evidence:** Anthropic blog: "sorting a list via token generation is far more expensive than simply running a sorting algorithm … many applications require the deterministic reliability that only code can provide." Docs: "instructions for flexible guidance, code for reliability, resources for factual lookup." AugiCraft README levels: Level 0 trusted tools (code, tested), Level 2 learned plans (Markdown, agent-written). `kb_save_skill` "rejects code". SkillForge made the same choice in production: no `scripts/`, only "pre-defined, verified system tools". Checked: blog, docs, repo, SkillForge §2.2.
- **Chris's own line:** "Best when you need code." ([[2026-01-17 - Learning Claude Skills]]).
- **Visual:** the cartridge splits into a steel core (code) and a paper label (steps).

## The takeaway

Don't ask Claude to write a skill before it has done the task. After a session where it got something right, ask it to save the procedure from what actually happened, with the failure modes it hit, and write the description as a trigger ("use when…"). Treat it as a draft until it works a second time.

## Bridge

A skill gets promoted only when it passes a check. That check, the test or eval that says "this worked," is the pipe that matters most, and it's the next episode.

## Extra material (for a long cut or a written companion)

- **Prior art: Voyager (2023).** An LLM agent in Minecraft with "an ever-growing skill library of executable code", an automatic curriculum, and self-verification. It got "3.3x more unique items" and reached tech-tree milestones "up to 15.3x faster than prior SOTA" (abstract only). AugiCraft's README says it is "Inspired by Voyager, with one change: Augi doesn't pile up bigger and bigger programs. It keeps a small set of trusted tools and learns Markdown plans and lessons that compose them." AugiCraft also imports 51 Voyager skills as `unverified` reference.
- **SkillForge (SIGIR 2026 Industry Track; cloud tech support at a major cloud provider).** 5 scenarios, 1,883 tickets, 3,737 tasks. Skills built from domain tickets beat a generic skill creator by +4.3 pp "Strict CR" (an LLM-judge consistency rate with expert replies; the judge had >90% agreement with two human experts). A three-step loop (Failure Analyzer → Skill Diagnostician → Skill Optimizer) rewrote skills from batches of bad cases. Over three rounds it gained 9–12 pp from every starting point, including expert-written skills (+10.99). Gains shrank each round (expert start: +4.09/+5.55/+1.35). Tool and style errors kept falling, but knowledge errors plateaued after round 1. v3 beat the legacy production system by +13.76 pp. Lesson for the companion: evolution from real failures works, and it hits a ceiling on tacit knowledge, which is why a human still reviews.
- **MemSkill (Zhang et al., Feb 2026).** Turns memory operations (what to extract, consolidate, prune) into a skill bank. An RL-trained controller picks a few skills per span, an LLM executor applies them, and a "designer" periodically mines hard cases to refine and add skills. It keeps snapshots and "roll[s] back if an update degrades performance". ALFWorld with LLaMA-3.3-70B: 80.36% average success, +5.53 over the best baseline (LightMem). Transfer to Qwen without retraining: 81.29%. It also transferred from LoCoMo to LongMemEval and HotpotQA. Relevance: skills aren't only for tasks. The rules for what to remember can be skills too, and they can be learned.
- **Focused beats exhaustive.** SkillsBench: "Focused Skills with at most three modules outperform larger or exhaustive bundles, and smaller models with Skills can match larger models without them." Curated skills are not always good. In v1, 16 of 84 tasks got worse with them, and domain gains ranged from +4.5 pp (software engineering) to +51.9 pp (healthcare).
- **Discovery is half the battle.** The description is the trigger. In SkillsBench's audit most self-written packs were never even opened. The survey's "weak trigger specification": "the skill itself may be useful, yet still fail in deployment because it is routed poorly." Practical tip: write descriptions as "Use when …" with the words a user would actually type.
- **Security.** Anthropic: "We recommend installing skills only from trusted sources." The docs: "Treat like installing software." The survey cites PoisonedSkills: third-party skill docs can hide malicious logic. Ties to Chris's own supply-chain rules. Skills from a marketplace are dependencies.
- **Where skills live in Claude Code:** `~/.claude/skills/` (personal) or `.claude/skills/` (project), shareable via plugins. Claude Code skills don't sync with claude.ai or the API. Skills became an open standard on 2025-12-18 (blog update line).
- **LangChain turned trace analysis into a skill.** "wanted trace analysis to be repeatable, so we made it into an Agent Skill. This became our recipe to analyze errors across runs and make improvements to the harness." ([[Improving Deep Agents With Harness Engineering]], Readwise). A skill that improves the harness is the bridge to ep 8.
- **The ladder framing.** "Prompts expire. Loops run. Skills compound." It's Extended_Brain's, as distilled in [[2026-06-12 - Draft - Self-Improving Loops and AutoResearch]]. Chris's own note on it: "The skills-ladder taxonomy (prompts/loops/skills) → one passing line max; it's Extended_Brain's frame, not mine". Use it once, attributed.
- **Ecosystem scale (survey Table I, unverified by us):** SkillsMP 700k+, SkillNet 300k+, Skills.sh 90k+, SkillHub 80k+, ClawHub 40k+ skills. Big libraries make retrieval and quality control the hard part.
- **Chris's daily version:** `claude-skills-private` (the `~/.claude/skills` symlink). Worth one shot of `ls` in the companion. Don't claim anything about which of those skills were agent-written; not checked.

## Don't say

- "Self-written skills don't work." SkillsBench tested skills written *before* solving, from the model's priors. It did not test skills distilled from a successful run. Say "skills an agent writes up front, before doing the work."
- "Claude Code got 8% worse." It's −8.1 percentage points, and that config ran the self-generated condition at effort "max" vs baseline "high". The authors keep it "as a diagnostic", outside the main aggregate, and the deficit "mixes content quality with skill-discovery and creator/solver interference effects."
- "My bot learned doors, climbing and fighting by itself, and they're proven." Only the door skill and livestock hunting are `validated` (2 successes each). Climbing (`navigate-and-repair-mine-stairs`) is a candidate with 1 success and 1 failure. One self-defense skill was deprecated. Also, a "manager" agent installed part of the door fix (episode 16-59-36), so "the agents" is more accurate than "the bot".
- "Validated after two runs on different days." Both door successes are logged on 10/12, seconds apart. They're two separate runs recorded back to back. The gate is light. Say "a second separate run."
- "MemSkill (NeurIPS '26)." arXiv lists no venue, and the HTML uses the ICML template. Venue unverified.
- "Skills are just prompts." The docs contrast them: prompts are "conversation-level instructions for one-off tasks"; skills "load on demand."
- Exact Voyager numbers as if checked in the paper body. They're abstract-only.
- "Agent Skills from the Perspective of Procedural Memory" (TechRxiv, Jan 2026). Not found or read. Leave it out.
